## EF-05 — Add a CI drift check for the generated tool catalog

**Value: Medium · Effort: Low · Owner: unassigned**

`scripts/lib/setup-tool-catalog.generated.sh` is generated by
`scripts/setup-tool-catalog.py` from `config/setup-tool-catalog.json` and consumed
by `scripts/interactive-setup.sh`. No workflow in `.github/workflows/` references
the generated file, so nothing verifies that it matches its source.

This matters more than it looks, because feature 031's T000 introduces a second
registry (`config/provider-credential-capabilities.json`) while
`config/setup-tool-catalog.json:1518` already carries a `kimi_code` row with
`access='api unknown'`, `type='frontier unknown'`, `native='llm video unknown'`
and `via='unknown'`. That is finding F7. An unchecked generated artifact sitting
between two overlapping registries is the likeliest source of a "correct in
config, wrong in the TUI" defect.

**Proposed change**: add a regenerate-and-diff gate that fails when the committed
generated file differs from a fresh generation. Resolve F7 alongside it by
declaring which registry is authoritative for credential capability — drafted
wording is in the
[proposed-edits document](../specs/031-kimi-glm-profile-credentials/review-2026-10-24-qwen-proposed-edits.md).

**Done when**: CI fails on a stale generated catalog, and one document states
which registry governs credential capability.

## EF-06 — Retrofit the projection adapter interface to the existing four providers

**Value: Medium · Effort: Medium · Owner: unassigned**

Feature 031's FR-017 defines the right interface — `inspect`, `extract`,
`validate`, `fingerprint`, `merge/install` — and correctly identifies that
`scripts/credential_sync_client.py` currently hashes and replaces **whole**
credential files, verified at its use of `read_json`, `atomic` and
`digest(downloaded['credential'])`.

But FR-017 is scoped to Kimi and GLM only. The four providers already covered by
`credential-container/credential_recovery.py` — Claude, Codex, Pi and OmniRoute —
retain whole-file semantics. The bug class the contract fixes for GLM, where an
unrelated provider edit becomes a publication or a restore clobbers neighbouring
records, therefore **still exists for those four providers today**.

**Proposed change**: extend the FR-017 adapter interface to all six providers so a
single dialect exists, with projection fingerprint separated from backing-file
revision throughout.

**Done when**: no provider path in recovery or sync replaces a whole credential
file, and unrelated-record preservation is tested per provider.

**Why 1.7.1 and not 1.7.0**: it is remediation of pre-existing behaviour rather
than a prerequisite for 031. Doing it while the interface is being built is
cheaper than after two dialects exist, so it should follow 031 closely rather than
drift.

## EF-07 — Pin AI CLI versions and emit a build manifest

**Value: Medium · Effort: Medium · Owner: unassigned**

`base-image/install-ai-clis.sh` installs **nine** packages at `@latest`:

```text
@anthropic-ai/claude-code   @openai/codex          @qwen-code/qwen-code
@moonshot-ai/kimi-code      @deepseek-ai/dsh       aider-chat
@ampcode/cli                @letta-ai/letta-code   ai/coding-helper
```

The Kimi install is at line 283. Every qualification matrix in feature 031's T000
and every "exact client version" evidence row required by SC-005 and FR-022 rests
on versions that a plain image rebuild can silently change.

`plan.md` deliberately excludes pinning — "No source pins, live credentials or
cloud resources change here" — and FR-020 mitigates through detect-and-requalify.
That is internally coherent, but it makes qualification evidence perishable by
construction, and `research.md` already notes that "reusing an image does not
prove its installed version".

**Proposed change**: pin versions in the image recipe and emit a build-time
manifest of actually-installed versions. Have the runtime compare the manifest
against the qualified capability matrix, which turns FR-020's "a stale receipt or
version string alone is not qualification" from a caution into an enforced check.

**Done when**: two builds from the same commit produce the same CLI versions, and
a version mismatch against the qualified matrix is detected rather than assumed
away.

## EF-08 — Provider capability registry as a single declarative model

**Value: High · Effort: High · Owner: unassigned**

**Deliberate deferral — this is the one item where the "High goes to 1.7.0" rule
and the reviewer's recommendation diverge.** It is rated High value but is placed
in 1.7.1 because it is High effort and because feature 031 should land first: 031
is the registry's first consumer, and building the registry before 031 exists
would mean designing it against a hypothetical rather than a real second
implementation. Override this and pull it into 1.7.0 if you expect several more
providers soon.

The case for it is measured, not speculative. Provider support is currently
duplicated across subsystems with **almost disjoint coverage**:

| Subsystem | Providers found |
| --- | --- |
| `scripts/compose-ai-profiles.py` | claude, openai, gemini, grok, glm — no codex, pi or omniroute |
| `credential-container/credential_recovery.py` | claude, codex, pi, omniroute — no gemini, grok, glm or openai |
| `scripts/credential_sync_client.py` `managed_path()` | four hardcoded roots: `.claude-profiles`, `.chatgpt-profiles`, `.opencode-profiles`, `.pi-profiles` |

Only `claude` appears in all three. `config/setup-tool-catalog.json` separately
carries roughly 90 harness rows, many with `unknown` fields, and T000 adds a
fourth registry on top.

Feature 031 demonstrates the cost concretely: adding one provider drives tasks
T001–T007 across approximately twenty files spanning composer, normalizer,
launcher, mounts, adapters, recovery, broker, sync client and UI.

**Proposed change**: make `config/provider-credential-capabilities.json` the
single declarative provider model — identity, aliases, profile-home convention,
auth modes, projection schema, per-operation eligibility and recovery-store
support — and have composer, launcher, recovery adapters and the sync client
derive from it rather than maintaining their own lists. This also discharges
`research.md`'s request for "one capability registry rather than differently
interpreted mode strings", which currently has no normative home, and subsumes
EF-05's authority question.

**Done when**: adding a provider is a registry entry plus an adapter, with no edit
to a hardcoded provider list; and `managed_path()` derives its exclusions from the
registry instead of four literal paths.

**Sequencing**: belongs in its own OpenSpec change, with 031 as first consumer
rather than owner.

## EF-09 — Derive the active feature from the branch instead of a stale pointer

**Value: Low (housekeeping) · Effort: Low · Owner: unassigned**

`.specify/feature.json` contains `feature_directory: specs/018-clean-sync-benches`
while the worktree's branch is `031-kimi-glm-profile-credentials`. Feature 031's
`quickstart.md` works around this by instructing every reader to export
`SPECIFY_FEATURE` and `SPECIFY_FEATURE_DIRECTORY` manually, and warns "do not
rewrite it as a documentation side effect".

Because the branch name and the spec directory name are identical by convention,
the tooling can derive one from the other. Documenting a manual workaround for a
machine-solvable problem guarantees that someone eventually runs speckit tooling
against feature 018 by accident.

**Proposed change**: derive the active feature from the current branch name,
falling back to `.specify/feature.json` only when the branch does not match a spec
directory. Then delete the export incantation from the quickstart.

**Done when**: no feature document needs to tell the reader which environment
variables to export to address its own spec.

## EF-10 — Worktree lifecycle and pruning policy

**Value: Low (housekeeping) · Effort: Low · Owner: unassigned**

The host holds roughly **41 `workBenches*` directories** under `~/Projects`, plus
`speckit-worktrees/` containing at least 029, 031 and 032. Many are named as
release or QA candidates that are almost certainly finished —
`workBenches-1.6-qa-candidate`, `-1.6-release-merge`, `-1.6-team-gate`,
`-1.6-latest-test`, `-1.7-qa-version`, `-qa-automation-current` and similar. Which
are live was **not** determined during this review.

Beyond disk cost, this sprawl has already produced concrete harm: it is what made
finding F4 hard to diagnose, and it is the mechanism behind the stale-copy hazard
in EF-03, since every worktree carries a full copy of every spec directory.

**Proposed change**: a short written policy covering what a worktree is for, when
it is pruned, and which are currently live. An audit of the existing set should
precede any deletion — several may hold uncommitted work, and this review found
uncommitted edits in an active one.

**Done when**: the live set is identifiable at a glance and dead worktrees are
removed after confirming nothing uncommitted is lost.

**Caution**: pruning is destructive. Audit for uncommitted changes before removing
anything; do not treat age alone as evidence that a worktree is dead.

## EF-11 — Promote the secret-canary gate to shared CI

**Value: Low (housekeeping) · Effort: Low · Owner: unassigned**

Feature 031's SC-004 requires that canary secrets "never appear in captured logs,
metadata, arguments, images or release artifacts". That is a good gate and every
credential-touching feature needs it, but it is currently 031-local. Feature 032
and the existing 027 company-sync work have the same exposure.

**Proposed change**: extract the canary gate into a reusable workflow that any
credential-touching feature opts into, rather than restating the requirement per
spec.

**Done when**: at least two features consume the shared gate and neither restates
it locally.
