# Catalog design

Canonical `config/setup-tool-catalog.json` is internal presentation data, schemaVersion 2 (extended by setup-harness-filters). Each stable entry has one home category, a terminal ownership group when relevant, a separate model-policy field, tags, qualified metadata, primary evidence links where verified, and optional read-only detection hints. All supplied terminal products are represented once per distinct SKU, not once per execution mode. Existing references precede appended references in flat arrays so old indexes stay stable. Managed keys are exactly the existing eight Harness and seven Tools keys.

A deterministic Python validator/compiler emits `scripts/lib/setup-tool-catalog.generated.sh` (arrays, labels, About and group metadata) and `scripts/setup_tool_catalog_data.py` (reference detection). Both are generated, versioned and checked against canonical data by fixture verification. Runtime parsing/rendering never invokes JSON tools or compilers. Single-quoted shell literals and validated IDs prohibit executable metadata. No host-specific installation paths are stored. Standard desktop-file locations are resolved at runtime; Exec lines are read as data and only known launcher basenames/executable presence may count, never run.

The CLI list now uses the combinable F filter panel governed by setup-harness-filters. Frontier, Region, Access, Native and Via are independent multi-select dimensions; the original ownership groups remain a single-choice Group row. Values combine with OR within a dimension and AND across dimensions. P/G restores every selection, cursor and result/About offset; refresh and step navigation retain the filter view. Default is no active constraints. No top-level interoperability category exists.


About shows source qualification early and distinct interoperability fields: invokes agents/mechanism, external invocation, delegation, state exchange, parallel execution. Lack of evidence is labeled Not yet verified, never false or absent. Capability evidence describes documented features and does not certify the installed version. Manual inventory does not infer GUI installation from terminal binaries, legacy Kimi from Kimi Code, or every Qoder SKU from a shared command. Ambiguous/unintegrated detection returns needs-check. Desktop/editor presence is separate from account access. Previously supported native inventory and managed installer behavior are retained.

The 87×40 component view reserves at least five About lines even for a large CLI list; narrow frames still retain focus and bounds. Product labels/statuses compact at narrow widths, and CLI group names receive a separate row below 60 columns. Actual mise/pnpm regular .bin wrappers require the matching npm package name, declared command export and contained executable payload; a generic kimi executable alone proves neither product generation.

T039L supersedes the row/group filter presentation: exactly Type, Region, Access and Native single-choice columns remain above live results, with Frontier as the new-session default. Model-weight records qualify Open/Closed routes independently of harness licensing, retaining native/routed evidence separately in About. See setup-harness-filters for current keys and matching semantics.
